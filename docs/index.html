QZTMF Patterns

Reference Implementations of the Quantum-Safe Zero-Trust Migration Framework's Engineering Patterns

QZTMF is a seven-phase methodology for migrating enterprise zero-trust architectures to NIST post-quantum cryptographic standards. This repository ships working, tested code for the four engineering patterns the framework depends on: an Algorithm Abstraction Layer that makes an algorithm rotation a policy change instead of a code change, Dual-Signature Validation for the hybrid classical/post-quantum transition window, a Key Material Versioning schema for tracking which keys were issued under which migration phase, and the paper's Quantum Risk Score asset-prioritization formula.

What's here

Four patterns, one repository

Each pattern is a standalone module with its own tests: no shared framework runtime, no hidden coupling. Pull in the one you need.

1Algorithm Abstraction Layer

Resolves cryptographic operations by security level and operation type rather than by algorithm name. Ships a classical (RSA/ECDSA) backend via the cryptography package today, plus a register_backend() plug-in point for a post-quantum backend (e.g. an oqs-bound ML-DSA implementation), so swapping the algorithm is a policy rebind, not a call-site change.

qztmf_patterns/aal.py

2Dual-Signature Validation

The kid-based dispatch logic for the Phase 6 hybrid window: a token may carry a classical signature, a pure post-quantum signature, or a legacy signature with a parallel post-quantum extension over the same payload. Sits in front of any JWT/JOSE library rather than reimplementing one.

qztmf_patterns/dual_signature.py

3Key Material Versioning

A tagging schema and query surface (by migration phase, by algorithm family, expiring-within-N-days, classical fallback rate) for tracking which keys were issued under which QZTMF phase without cross-referencing multiple systems.

qztmf_patterns/key_versioning.py

4Quantum Risk Score

The paper's asset-prioritization formula, QRS = 0.5·AQV + 0.3·DSL + 0.2·ESB, with the weights exposed as a constructor argument. The paper is explicit that the default weights are a starting heuristic, not an empirically derived optimum. This module makes recalibration a parameter, not a code edit.

qztmf_patterns/qrs.py
Section IV.A

Quantum Risk Score

Ranks assets for migration priority. Each input is a normalized 0.0–1.0 signal; weights must sum to 1.0 and are validated at construction time.

Weighted formula

# AQV: algorithm vulnerability to Shor/Grover
# DSL: data sensitivity lifetime
# ESB: enterprise blast radius

QRS = 0.5 * AQV
    + 0.3 * DSL
    + 0.2 * ESB

Usage

from qztmf_patterns.qrs import \
    QuantumRiskScore

qrs = QuantumRiskScore()
qrs.rank({
    "root-ca": (1.0, 1.0, 0.9),
    "session-cache": (0.6, 0.1, 0.3),
})
# [('root-ca', 0.97), ('session-cache', 0.42)]
Phase 6

Dual-signature dispatch during the hybrid window

A relying party has to accept three token shapes at once during the classical-to-post-quantum transition. The dispatch rule is keyed off the token's kid, not a global feature flag.

Legacy classical key, no PQ extensionPhase 1–5 pre-hybrid state. Accepted, but treated as a migration-backlog signal, not steady state.
→
Legacy classical key + ext-ml-dsa-sigPhase 6 hybrid state. Both the classical and the post-quantum signature over the same payload must verify.
Post-quantum key alonePhase 7 target state. Verification rests entirely on the post-quantum signature.
→
Exit gateclassical_fallback_rate() tracks the key-population analogue of the paper's Phase 6→7 exit criterion.
Stated honestly

What's not here

  • The mTLS handshake latency and X.509 certificate size benchmarks reported in the paper were measured separately against Open Quantum Safe liboqs 0.10.1 on dedicated hardware. This repository does not reproduce those hardware measurements; it provides working reference implementations of the patterns themselves.
  • This is reference/research code accompanying an academic manuscript, not a production PKI library. Enterprise adopters should treat it as a starting point for their own Algorithm Abstraction Layer, not a drop-in dependency.
  • The post-quantum backend slot in the Algorithm Abstraction Layer is a plug-in interface, not a bundled ML-DSA implementation, so this package installs cleanly without an oqs/liboqs dependency.
